**Project:** Enterprise Hospitality Lakehouse Platform

**Version:** 1.0

**Author:** Sanjay K J

---

# 1. Purpose

This document defines the physical data storage strategy for the Enterprise Hospitality Lakehouse Platform.

It describes how datasets are organized, stored, optimized, and maintained throughout their lifecycle to support scalable analytics, reliable processing, and enterprise governance.

---

# 2. Storage Architecture

The platform follows a layered storage architecture aligned with the Medallion Architecture.

```text
Landing
    │
    ▼
Bronze
    │
    ▼
Silver
    │
    ▼
Gold
```

Each layer represents an increase in data quality and business value.

---

# 3. Storage Technologies

| Layer | Technology | File Format |
|--------|------------|-------------|
| Landing | Cloud Object Storage | CSV / JSON / Parquet |
| Bronze | Delta Lake | Delta |
| Silver | Delta Lake | Delta |
| Gold | Delta Lake | Delta |

Delta Lake is the standard storage format across all analytical layers.

---

# 4. Landing Zone

The Landing Zone stores source files exactly as received.

## Objectives

- Preserve original files
- Support replayability
- Enable auditing
- Prevent accidental modification

### Folder Structure

```text
landing/
├── reservations/
├── inventory/
├── pricing/
├── room_configuration/
├── property_master/
├── customer/
├── benchmark/
├── calendar/
└── metadata/
```

Files are immutable.

---

# 5. Bronze Storage

The Bronze layer stores raw source data after ingestion.

Characteristics:

- Delta format
- Append-only
- Source schema preserved
- Metadata enrichment
- Historical retention

Example:

```text
bronze/
├── reservation
├── pricing
├── inventory
├── room_configuration
├── customer
└── property_master
```

---

# 6. Silver Storage

The Silver layer stores standardized enterprise datasets.

Characteristics:

- Validated data
- Standardized schema
- Cleansed records
- Business rule enforcement
- Conformed dimensions

Example:

```text
silver/
├── reservation_clean
├── pricing_clean
├── inventory_clean
├── customer_dimension
└── hotel_dimension
```

---

# 7. Gold Storage

Gold datasets are optimized for business consumption.

Examples:

```text
gold/
├── fact_reservation
├── fact_revenue
├── fact_pricing
├── fact_occupancy
├── dim_hotel
├── dim_room_type
├── dim_calendar
└── daily_kpis
```

---

# 8. Storage Organization

The storage hierarchy follows a domain-oriented structure.

```text
catalog
│
├── bronze
│
├── silver
│
└── gold
```

Each catalog contains multiple schemas representing business domains.

Example:

```text
silver
│
├── reservations
├── pricing
├── inventory
├── property
└── customer
```

---

# 9. Table Design Standards

Every Delta table follows common design standards.

Required metadata columns:

| Column | Purpose |
|---------|----------|
| batch_id | Processing batch |
| ingestion_timestamp | Load timestamp |
| source_system | Originating system |
| load_date | Processing date |
| pipeline_name | Pipeline identifier |

---

# 10. File Organization

Large datasets are automatically divided into multiple files.

Objectives:

- Parallel processing
- Efficient reads
- Faster writes
- Better scalability

Small files are periodically compacted.

---

# 11. Compression

Delta Lake automatically stores data using Parquet compression.

Benefits include:

- Reduced storage cost
- Faster scans
- Better IO throughput

---

# 12. Partitioning Strategy

Tables are partitioned only when they provide measurable performance benefits.

Typical partition columns:

- Business Date
- Property
- Country
- Market

Partition selection is based on expected query patterns.

---

# 13. Schema Evolution

Supported changes include:

- New nullable columns
- Optional attributes
- Metadata additions

Breaking schema changes require controlled deployments.

---

# 14. Time Travel

Delta Lake enables historical data access using Time Travel.

Use cases include:

- Recovery from accidental updates
- Historical reporting
- Audit investigations
- Pipeline debugging

---

# 15. Storage Optimization

Optimization activities include:

- File Compaction
- Statistics Collection
- Data Skipping
- Partition Pruning

These operations improve query performance while reducing storage overhead.

---

# 16. Storage Lifecycle

```text
Source
   │
Landing
   │
Bronze
   │
Silver
   │
Gold
   │
Consumption
```

Each layer has independent ownership and lifecycle management.

---

# 17. Monitoring

Storage monitoring includes:

- Table size
- Growth rate
- File count
- Storage utilization
- Partition distribution
- Data freshness

Alerts are generated when predefined thresholds are exceeded.

---

# 18. Design Principles

- Immutable raw storage
- Open storage format
- Layered architecture
- Domain-oriented organization
- Metadata-driven design
- Scalability by default
- Cost-efficient storage

---

# 19. Summary

The storage architecture provides a scalable and governed foundation for enterprise analytics. By standardizing on Delta Lake and organizing datasets using Medallion principles, the platform supports reliable ingestion, efficient processing, simplified governance, and high-performance analytical workloads.
