# Repository Structure

This document defines the standard repository layout for the Enterprise Lakehouse Platform.

The objective is to maintain a clean, scalable, and production-ready project structure that supports collaborative development, CI/CD, infrastructure automation, and enterprise-grade data engineering practices.

The folder hierarchy defined here is considered the single source of truth for the repository organization.

---

# Repository Structure

```text
enterprise-lakehouse-platform/

│
├── .github/
├── configs/
├── dashboards/
├── datasets/
├── docs/
│
├── monitoring/
├── pipelines/
├── samples/
├── scripts/
├── src/
├── terraform/
└── tests/
```

---

# Folder Overview

## .github/

Contains GitHub-specific configuration and automation.

Examples:

- GitHub Actions
- Pull Request templates
- Issue templates
- CI/CD workflows

---

## configs/

Stores all configuration files used across environments.

Examples:

- dev.yml
- qa.yml
- prod.yml
- pipeline.yml
- logging.yml

No environment-specific values should be hardcoded inside Python code.

---

## dashboard/

Contains the source code for operational dashboards.

Examples:

- Pipeline execution dashboard
- Data quality dashboard
- Monitoring UI

---

## dashboards/

Contains exported dashboard definitions.

Examples:

- Databricks SQL dashboards
- Power BI templates
- Dashboard JSON exports

---

## datasets/

Contains metadata describing datasets used throughout the platform.

Examples:

- Dataset definitions
- Schema documentation
- Sample metadata
- Business data dictionary

This folder does **not** contain production data.

---

## docs/

Contains all functional, architectural, and design documentation.

```text
docs/

04_Architecture/
05_Data_Architecture/
06_Low_Level_Design/
```

As the project evolves, additional folders such as `01_Business` and `02_Requirements` can be introduced while preserving the same structure.

Documentation is version-controlled alongside the implementation.

---

## monitoring/

Contains monitoring and observability assets.

Examples:

- Alert definitions
- Metric configurations
- Monitoring notebooks
- Health checks

---

## pipelines/

Contains orchestration definitions.

Examples:

- Databricks Workflows
- Pipeline configuration
- Job dependencies
- Execution schedules

This folder defines **how** pipelines execute, not the business logic itself.

---

## samples/

Contains synthetic datasets used for local development and testing.

Examples:

- Reservation sample data
- Inventory sample data
- Pricing sample data

No production or sensitive data should be stored here.

---

## scripts/

Contains reusable utility scripts.

Examples:

- Environment setup
- Data generation
- Local testing utilities
- Deployment helpers

Scripts should be independent and executable without modifying source code.

---

## src/

Contains all production data engineering code.

Current structure:

```text
src/

bronze/
silver/
gold/
```

### bronze/

Implements ingestion logic.

Responsibilities include:

- Reading source systems
- Schema validation
- Initial data loading
- Raw Delta table creation

---

### silver/

Implements business transformations.

Responsibilities include:

- Data cleansing
- Standardization
- Deduplication
- Business rules
- Conformed datasets

---

### gold/

Implements business-ready data models.

Responsibilities include:

- Star schema generation
- Fact tables
- Dimension tables
- KPI calculations
- Reporting datasets

As the project grows, shared modules (for logging, utilities, configuration, and reusable framework components) may be introduced under `src/` while maintaining backward compatibility.

---

## terraform/

Contains Infrastructure as Code.

Examples:

- Databricks Workspace
- Unity Catalog
- Storage Accounts
- IAM Roles
- Networking
- Key Vault

Infrastructure changes should be managed exclusively through Terraform.

---

## tests/

Contains automated testing assets.

Recommended organization:

```text
tests/

unit/
integration/
performance/
```

Every production module should have corresponding automated tests.

---

# Repository Design Principles

The repository follows these principles:

- Separation of concerns
- Modular implementation
- Configuration-driven development
- Infrastructure as Code
- Documentation alongside implementation
- Automated testing
- CI/CD readiness
- Environment portability

---

# Development Guidelines

The following rules apply throughout the project:

- Business logic belongs in `src/`.
- Pipeline orchestration belongs in `pipelines/`.
- Configuration belongs in `configs/`.
- Infrastructure belongs in `terraform/`.
- Documentation belongs in `docs/`.
- Test code belongs in `tests/`.
- Sample data belongs in `samples/`.

No production code should depend directly on documentation or sample datasets.

---

# Future Evolution

The repository is intentionally designed to evolve incrementally.

As additional capabilities such as reusable frameworks, shared utilities, or advanced monitoring are introduced, new modules may be added without requiring major restructuring of the existing repository.
